# Pet Service

The Pet Service owns the Pet bounded context: owner contact records, pet identity and medical-profile metadata, and the ownership-verification contract used by Appointment Service. It is an independent .NET 10 microservice with its own PostgreSQL database; other services never access its tables or domain entities directly.

## Architecture and domain model

The service follows Clean Architecture:

- `PetService.Domain` contains the `Owner` and `Pet` aggregates, `PetName` and `MicrochipNumber` value objects, `PetSpecies`, invariants, and domain exceptions. It has no framework dependencies.
- `PetService.Application` contains commands, queries, request/response DTOs, FluentValidation validators, repository abstractions, mapping, and use-case handlers.
- `PetService.Infrastructure` implements the repositories and unit of work with EF Core/Npgsql, owns migrations and deterministic demo seed data, and registers the service in Consul.
- `PetService.Api` exposes secured REST controllers, RFC 7807 error responses, JWT/Keycloak authentication, role authorization, OpenAPI/Swagger, and health checks.

An owner has a required name, normalized valid email, and a phone containing 7–15 digits. A pet must belong to an existing owner and have a name, known species, non-future birth date, and positive weight. Optional microchips are normalized to uppercase, contain 8–30 letters/digits, and are unique. Allergy and chronic-condition lists are trimmed and deduplicated. Deleting an owner cascades to that owner's pets.

## REST API

Swagger UI is available at `/swagger`; the OpenAPI document is `/openapi/v1.json`.

| Method and route | Roles | Purpose |
|---|---|---|
| `POST /owners` | `owner`, `admin` | Create an owner |
| `GET /owners` | `owner`, `admin` | List owners |
| `GET /owners/{id}` | `owner`, `admin` | Read an owner |
| `PUT /owners/{id}` | `owner`, `admin` | Update an owner |
| `DELETE /owners/{id}` | `owner`, `admin` | Delete an owner and their pets |
| `GET /owners/{ownerId}/pets` | `owner`, `admin` | List one owner's pets |
| `POST /pets` | `owner`, `admin` | Register a pet |
| `GET /pets` | `owner`, `admin` | List pets |
| `GET /pets/{id}` | `owner`, `admin` | Read a pet |
| `PUT /pets/{id}` | `owner`, `admin` | Update a pet |
| `DELETE /pets/{id}` | `owner`, `admin` | Delete a pet |
| `GET /pets/{id}/exists?ownerId={ownerId}` | `owner`, `admin`, `service` | Minimal ownership-verification contract |
| `GET /api/pets/{id}/exists?ownerId={ownerId}` | `owner`, `admin`, `service` | Compatibility route used by the existing Appointment client/Pact |
| `GET /health` | anonymous | Readiness, including database health |
| `GET /health/live` | anonymous | Process liveness |

Validation failures return `400`, missing resources return `404`, duplicate microchips return `409`, unauthenticated calls return `401`, and calls without an allowed role return `403`.

## Appointment Service integration

Appointment Service's unchanged anti-corruption client currently calls:

```http
GET /api/pets/{petId}/exists?ownerId={ownerId}
Authorization: Bearer <service token>
```

Pet Service supports both `/api/pets/...` and `/pets/...`, so route alignment does not require an
Appointment source change. The response deliberately exposes no internal pet or owner model:

```json
{
  "exists": true,
  "ownedByOwner": true
}
```

A missing pet returns `404`. An existing pet owned by somebody else returns `200` with
`exists: true` and `ownedByOwner: false`. Pet Service validates Keycloak tokens and permits the
`service` realm role on this endpoint. Pet Service also registers itself in Consul with `/health`.

Appointment Service still has its own outstanding work: it currently uses fake verification in
development/Docker, its real client uses a locally signed placeholder token, and its Pet HTTP
client does not yet use Consul discovery. Those are Member 2 responsibilities in
`TEAM-FINAL-TASK-HANDOFF.md`; Pet Service does not weaken JWT validation to accept the placeholder.

The consumer contract is generated by `tests/AppointmentService.PactTests`.
`PetService.Api.IntegrationTests` verifies all three checked-in Pact interactions without changing
the Appointment-owned Pact. Because that Pact reuses the same IDs and has no provider states, the
provider suite filters and prepares each interaction independently.

## MCP contribution

The shared MCP server registers two Pet-owned tools:

- `get_pet(petId)` calls `GET /pets/{petId}`.
- `get_owner_pets(ownerId)` calls `GET /owners/{ownerId}/pets`.

Their tool registration, response mapping, downstream paths, and bearer-token forwarding are covered by `tests/MCPServer.IntegrationTests`.

## Running and testing

Start the platform dependencies and services with `docker compose up --build`. Pet Service is exposed at `http://localhost:5101`; its PostgreSQL database is private to the service. Deterministic demo IDs are:

- owner: `33333333-3333-3333-3333-333333333333`
- pet: `44444444-4444-4444-4444-444444444444`

Run the Pet-owned suites and provider-side contract verification with:

```powershell
dotnet test PetService/PetService.Domain.Tests/PetService.Domain.Tests.csproj
dotnet test PetService/PetService.Infrastructure.Tests/PetService.Infrastructure.Tests.csproj
dotnet test PetService/PetService.Api.IntegrationTests/PetService.Api.IntegrationTests.csproj
```

The Appointment consumer Pact suite is owned by Member 2. Running it may regenerate the checked-in
Pact file, so coordinate any resulting contract change with that member.

## 30–45 second presentation summary

“I implemented the Pet bounded context as an independent Clean Architecture microservice. The domain protects owner contact data and pet rules such as valid names, species, birth dates, weights, and unique normalized microchips. EF Core persists the aggregates in a dedicated PostgreSQL database, while the secured REST API exposes owner and pet workflows. Appointment Service does not share our domain model: Pet exposes a minimal ownership-verification contract on both compatible route forms, validates the shared Keycloak roles, and registers itself in Consul. The shared MCP server also exposes `get_pet` and `get_owner_pets`. Domain, repository, API, health, authorization, MCP, and provider Pact tests cover the Pet-owned behavior.”
